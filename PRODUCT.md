# Product

## Register

product

## Users

SillyTavern roleplay users who want dialogue speakers to remain visually distinct in long, multi-character chats. They reach configuration from SillyTavern's extensions surface on desktop and mobile, open it as a full-window page, make the change they came for, and return to the chat. Configuration is a place they visit deliberately, not a panel that sits alongside the conversation.

## Product Purpose

Dialogue Colors assigns durable visual identities to character dialogue through solid colors, gradients, fonts, and local attribution. It should make conversations easier to follow while keeping setup safe, reversible, and unobtrusive. Success means users can understand the active engine and storage scope, process a chat confidently, edit a character quickly, and recover from consequential changes without leaving their roleplay flow.

## Brand Personality

Playful, vivid, friendly. Character color is expressive and meaningful, while controls remain familiar and concise.

## Anti-references

Do not turn the extension into a standalone analytics dashboard. Avoid card grids, decorative chrome, excessive status widgets, hidden expert gestures, or visual conventions that fight SillyTavern's host interface. Avoid using color as the only way to communicate state or speaker ownership.

## Design Principles

1. Keep the chat primary. Configuration is a full-window page, so it must be transient: entered in one action, left in one action, and never persistent over the chat. Sections earn the width to be readable without nested scrollers, but the page still opens on a single task and closes back to where the user was. Breadth of settings is not a license for the page to become somewhere users linger.
2. Make consequential behavior explicit. Storage scope, replacement, cleanup, and chat rewriting must state their target before acting.
3. Let character identity carry the expression. Use vivid color and gradients for speakers, not as decoration across ordinary controls.
4. Prefer familiar controls over clever gestures. Every action available by pointer should have an understandable keyboard and touch path.
5. Preserve trust through compatibility and recovery. Existing records remain available, changes are reviewable, and destructive operations have a clear undo path.

## Accessibility & Inclusion

Target WCAG 2.2 AA. Support keyboard navigation, visible focus, programmatic labels, announced status and validation, measured text contrast, reduced motion, forced colors, non-color speaker cues, 200% text zoom, and reliable touch targets. Desktop and mobile are equally important, including narrow desktop side panels where viewport breakpoints do not describe the available panel width.
